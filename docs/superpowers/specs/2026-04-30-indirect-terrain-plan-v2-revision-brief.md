## Decided architectural questions (apply verbatim — do not relitigate)

### A. Multi-bucket strategy = (i) SOLID-ONLY for PR1

- Indirect path retires CPU SOLID main-emit setup only.
- Detail (`addVertices(MC2_DRAWALPHA)`), overlay (`gos_PushTerrainOverlay`),
  and mine state STAY on legacy paths in this slice.
- Detail/overlay/mine consolidation is a future follow-up slice with
  its own brainstorm; flag it in the plan's "out of scope" section.

### B. quadSetupTextures gate-off = (i) NARROWED TO SOLID

- When `MC2_TERRAIN_INDIRECT=1` AND indirect path is preflight-armed
  for the frame (per C below): SKIP legacy SOLID main-emit setup
  branch in `setupTextures()`.
- KEEP detail/overlay/mine setup paths running.
- This requires identifying the EXACT code-level branch in
  `setupTextures()` (mclib/quad.cpp:429+) that is SOLID-only and
  safe to bypass. Plan v2 must cite line numbers and quote the
  branch boundary.

### C. DrawIndirect failure handling = (iv) PREFLIGHT-ARMED BYPASS

- Decide once per frame at a hook before the legacy SOLID setup
  loop runs whether indirect is "armed":
  ```cpp
  terrainIndirectSolidArmed = IsEnabled()
      && isDenseRecipeReady()
      && resourcesReady()
      && !inMissionTransition();
  ```
- If armed: legacy SOLID branch early-outs; indirect path draws.
- If not armed: legacy SOLID branch runs; indirect path skips draw.
- One bool check per quad — same pattern as M2's `fastPathEligible`.
  Cost is shipped infrastructure, not new design.

## Required mechanical fixes (M1–M8)

All from adversarial-review findings; each must be applied with grep-
verified citations.

### M1. Correct `TerrainQuadRecipe` description (Task 2.1)

- GREP `gos_terrain_patch_stream.h` for `TerrainQuadRecipe`. Cite
  file:line and the actual struct layout (9 vec4s).
- terrainType is packed into `_wp0.w` via reinterpret-cast (read
  by thin VS:122 as `floatBitsToUint(rec.worldPos0.w)`). Document
  this.
- terrainHandle / uvMode / mineState are NOT recipe fields. Remove
  all references to them as recipe fields. They live on the thin
  record (flags bits) or on `MissionMap::tileMineCount`. Cite
  where each actually lives.

### M2. Correct `invalidateTerrainFaceCache` strategy (Task 2.4)

- GREP `MapData::invalidateTerrainFaceCache` — confirm signature
  is `void invalidateTerrainFaceCache(void)` (mapdata.h:220).
- 4 callers exist; 2 are whole-map (destroy, newInit).
- Plan v2 must NOT change this signature.
- Add NEW per-entry API:
  ```cpp
  void invalidateRecipeForVertexNum(int32_t vn);  // precise sites
  void invalidateAllRecipes();                    // whole-map sites
  ```
- Map each existing call site to one of: precise (use vertexNum),
  whole-map (rebuild dense recipe), no-op (irrelevant to dense recipe).

### M3. Specify SSBO binding slots

- GREP `gos_terrain_thin.vert` for `binding =`. Confirm RecipeBuf=1,
  ThinRecordBuf=2 (gos_terrain_thin.vert:9,18).
- Indirect path's plan must explicitly state binding slots used.
- If indirect path needs additional SSBO (e.g., `glDrawElementsIndirect`
  command buffer), allocate slot, document, confirm no conflict
  with existing bindings.

### M4. AMD attribute 0 trap

- Add `glEnableVertexAttribArray(0)` requirement to the indirect
  bridge spec.
- Per `docs/amd-driver-rules.md:5`, vertex attribute 0 must be
  enabled or AMD drops draws silently.
- VAO 0 binding alone is insufficient.

### M5. `glColorMask` save/restore

- The indirect bridge bypasses `applyRenderStates`. Save current
  `glColorMask` state on entry; restore on exit.
- Same pattern as renderWater bridge — cite the precedent in
  `gos_render_water_fastpath.cpp` (or equivalent shipped file).

### M6. Per-mission teardown hook

- GREP `TerrainPatchStream::init` and `TerrainPatchStream::destroy`.
  Confirm these are wired to `gosRenderer` process-lifetime hooks,
  NOT per-mission.
- Plan v2's `event=recipe_teardown` must hook a real per-mission
  call site. Candidates: `Terrain::destroy()` (terrain.cpp:659) or
  a new `Terrain::resetForMission()`.
- WaterStream's actual pattern is "keep buffer, CPU-clear state per
  mission" — confirm the dense recipe uses the same pattern, not
  "destroy + recreate." Cite the WaterStream call site as
  precedent.

### M7. `event=first_draw` mission-latch (depends on M6)

- Once M6 lands a real per-mission reset hook, the mission-latch
  reset point is defined. Wire `first_draw` to fire once per mission,
  not once per process.

### M8. Verify `_cbbuf` size

- GREP wherever `_cbbuf` is declared. Confirm size is correct for
  the indirect command buffer (one `DrawElementsIndirectCommand`
  per drawn batch).

## New required additions (N1–N4) — scope-realignment from orchestrator

### N1. Counters for Gate B verification

Add three counters to the parity/debug gate set:
- `legacy_solid_setup_quads` (should drop to ~0 when armed and B(i) is correct)
- `indirect_solid_packed_quads` (should match legacy_solid_setup_quads pre-gate-off)
- `legacy_detail_overlay_quads` (should remain non-zero — detail/overlay stay legacy)

Without these, Gate B can pass on "renderer time went down" while
completely missing the CPU-offload goal (e.g., GPU got faster but
legacy CPU still iterates).

### N2. Stage 3 partial-landing hazard rule

Plan v2 must include an EXPLICIT rule: "Stage 3a (indirect draw
shipped) and Stage 3b (legacy SOLID gate-off shipped) MUST land in
the same PR. Do not land 3a alone — it can pass visual + smoke gates
while completely missing the CPU-offload goal."

### N3. Brainstorm Q3 addendum

The brainstorm Q3 ("interaction with recipe SSBO + thin-record SSBO
— merge or stay parallel") inherited stale memory and didn't surface
the multi-bucket trap. Plan v2 must include a one-paragraph addendum
citing brainstorm Q3 and stating: "Q3's answer is narrowed at plan
time to 'parallel for SOLID-PR1; multi-bucket consolidation deferred
to follow-up slice with its own brainstorm.'"

### N4. Stage 4 cross-mission validation

The 4-gate ladder's Gate D (tier1 5/5 PASS) currently runs in three
config triples (UNSET / FAST=1 / FAST=1+PARITY=1). For Stage 4
promotion (default-on flip), expand to a quintuple validating
cross-mission state under default-on:
- Default-on warm boot (run mc2_01 → mc2_03 → mc2_10 → mc2_17 → mc2_24
  in one process)
- Default-on cold start each mission

Mission-transition state cleanup is the failure mode this gate exists
to catch — per M6, per-mission teardown is non-trivial.
