# Render Contract Audit — 2026-05-14

## Scope
- Audited document: `docs/render-contract.md`
- Implementation files compared: `mclib/render_contract.{cpp,h}`, `shaders/include/render_contract.hglsl`, `scripts/check-render-contract-gbuffer1.sh`
- Cross-referenced: `.planning/codebase/ARCHITECTURE.md` (2026-05-14), `MEMORY.md` index + render-cluster topic files (`render_functions_are_enqueuers_not_submitters.md`, `mc_texture_manager_dual_queue_legacy_retirement_debt.md`, plus skimmed Track A/B/C, substrate, water, GPU-direct entries)
- Methodology: grep-verified each cited symbol in current code; reading-not-skimming for the contract doc. Every file:line below was re-grepped during this audit (line numbers in the contract doc itself are not file:line — they are markdown bullet items).

## Summary

The audited "render contract" is in fact **two unrelated artifacts that share a name**, and neither one has kept pace with the codebase as it stands on 2026-05-14:

1. **`docs/render-contract.md`** — a high-level *coordinate-space / submission-space* contract (world vs projected vs screen; A/B/C/D bucket taxonomy). This is the older, conceptual document. Its A/B/C buckets refer to *submission spaces*, not to the "Track A/B/C" modernization slices everyone now uses that vocabulary for.
2. **`mclib/render_contract.{cpp,h}` + `shaders/include/render_contract.hglsl` + `scripts/check-render-contract-gbuffer1.sh`** — a *Render Contract Registry* implementation (PassIdentity enum, ShadowContract / PassStateContract structs, GBuffer1 alpha = post-process shadow mask convention). Phase-1 inert, half-populated with TODO sentinels for everything that isn't terrain-adjacent or static-prop. Spec is `docs/superpowers/specs/2026-04-26-render-contract-registry-design.md`.

The high-level doc (item 1) is roughly half-stale: the priority-1 problem it calls out ("terrain visibility metadata depends on `projectZ()`") has been substantially addressed in `terrain.cpp` (no `projectZ` callers remain in that file; the callsite identity now lives in `quad.cpp` per the projectz containment design). The registry (item 2) is correctly self-described as inert phase-1, but it is silent on the broader frame architecture: queue model, enqueue-vs-submit, MLR exception, Track A/B/C modernization slices, dual-queue retirement debt, compute cull, substrate coalesce. None of those appear in either artifact.

The biggest single gap is that **neither artifact covers the actual structure of how the renderer works** — the dual master-node queues, the enqueue convention, the MLR immediate-draw exception, post-`renderLists` hook ordering — even though those have settled into stable, load-bearing architectural knowledge over the last six weeks of work.

## CONFIRMED — Contract claims that still match current code

- *"`MC_TextureManager` owns `masterVertexNodes` (legacy) and `masterHardwareVertexNodes` (modern) and flushes them in `renderLists`."* — Both arrays exist and are flushed in `mclib/txmmgr.cpp:1331` (`renderLists` definition); legacy array allocation at `mclib/txmmgr.cpp:261`, hardware at `mclib/txmmgr.cpp:267`; hardware-walk loop at `mclib/txmmgr.cpp:1435+`, legacy terrain shadow walk at `mclib/txmmgr.cpp:1505+`. This is implicit in the high-level doc but spelled out clearly in `ARCHITECTURE.md` and the dual-queue memory.
- *"Water surface and detail are intentional projected paths; do not migrate piecemeal."* (`docs/render-contract.md` §B1) — `mclib/quad.cpp` still has the per-quad projectZ scratch comment cluster (`mclib/quad.cpp:51`, `:363`, `:618`, `:922`); water shader pair `shaders/gos_tex_vertex.{vert,frag}` still active. The water-SSBO fast path (`water_ssbo_pattern.md`) supplements but does not replace this submission space.
- *"Grass shares the terrain world-space contract; forward-shaded."* (§A2) — `shaders/gos_grass.frag:70` writes `rc_gbuffer1_shadowHandled(bladeNormal)`, matching the terrain self-shadow convention from the registry.
- *"GBuffer1.alpha is a post-process shadow mask; shaders must route through `rc_*` helpers."* — Enforced by `scripts/check-render-contract-gbuffer1.sh` censuses 1/2/3; all 30 `GBuffer1 =` writesites in production fragment shaders use a registered `rc_*` helper (verified via grep).
- *"Terrain base, terrain decals, terrain overlays, and grass write alpha=1.0 (self-shadow); static props write alpha=0.0 (screen-shadow eligible)."* — Matches `render_contract.cpp:43,57,71,85` and `:99`. Shader-side: terrain/grass/overlay/decal use `rc_gbuffer1_shadowHandled*`; `mech.frag:76`, `static_prop.frag:147`, `gos_tex_vertex.frag:77` use `rc_gbuffer1_screenShadowEligible`.
- *"Legacy water/shoreline alpha overload is a documented contract violation contained to `gos_terrain.frag`."* — Three callsites: `shaders/gos_terrain.frag:646, :668, :704` use `rc_gbuffer1_legacyTerrainMaterialAlpha`; grep census enforces single-shader containment. The contract-violation framing in `render_contract.h:11-19` is accurate.

## STALE — Contract claims that no longer match current code

- *"`mclib/terrain.cpp` still uses `projectZ()` as the producer of terrain visibility metadata"* (`docs/render-contract.md` §A1 Current debt, §D1 Problem). **Severity: HIGH.** Grep of `mclib/terrain.cpp` returns zero `projectZ` references. The callsite identity is now contained in `mclib/quad.cpp` (per the projectz containment design `docs/superpowers/specs/2026-04-25-projectz-containment-design.md` and visible at `mclib/quad.cpp:51, 363, 618, 922`). The contract still flags this as the **Priority 1** cleanup item, but the cleanup has substantially progressed; the doc has not been updated.
- *"D1 (terrain world-space submission gated by projected depth) is the **highest-priority contract violation**."* **Severity: HIGH.** Track A1 shipped 2026-05-06 (object admission predicate, clip-space frustum, dual-output wrapper pattern) per `memory/track_a1_object_admission_predicate.md`, and the projectz containment design moved the load-bearing producer out of `terrain.cpp`. D1 as written ("terrain triangle acceptance depends on `pz`") needs re-scoping — the trace/overlay scaffolding (`mclib/projectz_trace.cpp`, `mclib/projectz_overlay.cpp`) exists specifically to track residual callsites, and the residual is no longer in `terrain.cpp`.
- *"D2 (IS_OVERLAY / `rhw=1.0` / terrainMVP bridge inside `gos_tex_vertex`) is active bridge, acceptable short-term."* **Severity: MEDIUM.** `shaders/gos_tex_vertex.frag:77` now writes `rc_gbuffer1_screenShadowEligible` — i.e. it has been formally pulled into the new registry as a contract-aware path rather than the loose "bridge state inside generic shaders" the doc describes. The bridge framing predates the registry's existence.
- *"D3 (post-process shadow pass for world geometry that should self-shadow) is a compatibility layer; target state is forward-shaded self-shadow for world geometry."* **Severity: MEDIUM.** The registry codifies the *opposite* split: terrain-family pixels self-shadow in their own shader (alpha=1.0), static props / mechs / generic objects deliberately route through `shadow_screen.frag` (alpha=0.0). This is now a *stable architectural decision*, not a bridge — `render_contract.h:13-15` and `render_contract.cpp:43,99` are explicit. The doc says the post-process path should not remain; the implementation says it is the chosen path for non-terrain-family geometry.
- *"Primary files for A1 include `code/gamecam.cpp` and `GameOS/gameos/gameos_graphics.cpp`"* (§A1). **Severity: LOW.** Both still exist; `gameos_graphics.cpp` still hosts the renderer core, and `gamecam.cpp` still drives the frame loop. The cite is fine, but the rest of A1's prose framing about "GPU tessellation via `terrainMVP`" omits the existence of the indirect-terrain draw work (`docs/superpowers/specs/2026-04-30-indirect-terrain-draw-design.md`) and the post-`renderLists` hook ordering rule.

## MISSING — Coverage the contract should have but doesn't

- **Dual-queue architectural debt** (`masterVertexNodes` + `masterHardwareVertexNodes` coexisting in `renderLists`). **Priority: HIGH.** The high-level doc never names either queue; the registry header acknowledges legacy material-alpha behavior but says nothing about the queue split. The authoritative source is currently `memory/mc_texture_manager_dual_queue_legacy_retirement_debt.md` (2026-05-14) and `.planning/codebase/ARCHITECTURE.md` §"Modernization fault lines". This is the *largest single piece of renderer-architectural knowledge* that has never been written into a real artifact — promotion target was captured 2026-05-14 in CLAUDE.md's "Pending durable artifacts" line.
- **"Render functions are enqueuers, not submitters" foundational principle.** **Priority: HIGH.** Same status as the dual-queue item: lives in `memory/render_functions_are_enqueuers_not_submitters.md` only. Every new contributor hits this; the contract is the natural home for it. Neither artifact mentions that `XXX::render()` enqueues into the master arrays vs `glDraw*` being deferred to `gos_RendererEndFrame -> renderLists`.
- **MLR's immediate-draw exception to the deferred-flush model.** **Priority: HIGH.** Documented only in `memory/render_functions_are_enqueuers_not_submitters.md`. `ObjectManager::render` at `code/objmgr.cpp:1650` is the canonical example. Anyone writing a GPU-direct fast path needs to know this *before* they hook anything in the render call sequence.
- **Post-`renderLists` hook ordering rule.** **Priority: HIGH.** "GPU-direct renderers must hook AFTER `renderLists()`" — see `memory/render_order_post_renderlists_hook.md` (referenced from MEMORY index). The high-level doc's "Migration Policy" is abstract; the operational rule that *actually* prevents broken fast paths is missing.
- **Track A/B/C modernization terminology and current status.** **Priority: HIGH.** The high-level doc uses "Bucket A/B/C/D" for *submission spaces*. Every plan/spec/memory file written since 2026-05-06 uses "Track A/B/C" for *modernization slices* (A1 = object admission predicate, B = static-prop registry widening, C = compute cull C0+C1a+C1b+C2+C3). This is a real terminology collision that confuses any reader who knows one vocabulary and meets the other. The contract should either (a) rename its buckets, or (b) explicitly cross-reference the Track terminology and where each Track lives in the contract's bucket model.
- **Compute cull pipeline and how it intersects the contract.** **Priority: MEDIUM.** `MC2_GPU_CULL_LIFECYCLE`, `MC2_GPU_CULL_SUBSTRATE`, the C3-6 / C3-9 sequence — all of this lives only in memory files and Track C entries. The contract has zero coverage of compute-cull's effect on visibility ownership (Rule 2). The contract names "GPU clip-space visibility" as a category but doesn't note that the GPU compute path is the *concrete current implementation* of that for static props.
- **Substrate coalesce path and the sync-stall lesson.** **Priority: MEDIUM.** `memory/substrate_coalesce_armed_multi_packet_limitation.md` (default-on as of `7b9ad5f`) and `memory/substrate_coalesce_sync_point_lesson.md` are operationally load-bearing. The contract is silent. At minimum the registry's `StaticProp` row should cross-reference the substrate path as the current submission mechanism.
- **The fact that there are two `render_contract` artifacts with the same name.** **Priority: HIGH.** Neither artifact mentions the other. A reader landing on `docs/render-contract.md` from a grep will not realize `mclib/render_contract.cpp` exists; a reader landing on the .cpp/.h will not realize there is a higher-level doc. Both should have a one-line "see also" at the top. The relationship between them (coordinate-space contract vs pass-identity-and-shadow-mask contract) should be stated.
- **GBuffer1 mask channel** (alpha = post-process shadow mask). **Priority: MEDIUM.** Lives in the .h/.hglsl/.sh trio and the registry spec, but the high-level `docs/render-contract.md` doesn't mention G-buffer at all. A reader of the high-level doc would not learn that there is a contractual convention for shadow eligibility.
- **`mcTextureManager->update()` cache eviction and the PAUSE/UNPAUSE diagnostic.** **Priority: MEDIUM.** Verified at `code/mission.cpp:507-510` (the not-paused gate). Load-bearing for debugging any "render bug clears on pause" symptom. Currently in `memory/pause_unpause_diagnostic_for_static_render_bugs.md` only.
- **Stock-install playability invariant** (`memory/stock_install_must_remain_playable.md`). **Priority: LOW.** Tangential to coordinate-space contracts but architecturally load-bearing for all renderer modernization. Could be a one-line "Non-Goal" addition: "removing graceful degradation when modern asset sidecars are missing."

## AMBIGUOUS / NEEDS-DISCUSSION — Contract and code disagree but it is unclear which is the authority

- **D3 status: bridge or stable choice?** The high-level doc says forward self-shadow is the target for world geometry; the registry says self-shadow is for terrain-family only and screen-space shadowing is the chosen path for mechs/static-props/generic objects. Which is the durable position? The registry is younger and more operationally grounded, but the high-level doc's framing (forward-shading-wherever-possible) is also defensible for performance reasons on a forward-shading-friendly path. User decision required.
- **Bucket A/B/C/D vs Track A/B/C nomenclature.** Rename buckets? Rename tracks? Cross-reference and live with the collision? All three are viable; the right choice depends on which vocabulary the user wants to be primary going forward.
- **Should `docs/render-contract.md` absorb the registry artifact's content, or stay separate?** Two artifacts is structurally messy; one giant doc has its own readability cost. CLAUDE.md's "Pending durable artifacts" item suggests a single consolidated doc at `docs/render-contract.md` or `.planning/codebase/RENDER-CONTRACT.md`. The registry's GBuffer1 mask convention and TODO sentinels would need a clear home in that consolidation.
- **Priority 1 ("remove terrain's dependency on projected-depth correctness") — is this done?** `terrain.cpp` no longer calls `projectZ`. `quad.cpp` still does, but the design that contains those callsites describes them as the *correct* residual location (containment, not removal). If the goal is "no terrain correctness dependency on `pz`," is the current `quad.cpp` containment the end state or a waypoint?
- **The contract calls B2 "Picking, cursor anchoring, and explicit screen-related helpers" intentional projected, but the cursor rework is pending** (`memory/cursor_rework_pending.md`, CRIT-1 against D-leaf-skip). When the cursor/picking rework lands, does its submission space change? If so, B2 needs a forward-looking note.

## Recommended next actions

1. **Decide artifact consolidation strategy.** Either merge the high-level doc and the registry into one consolidated artifact (CLAUDE.md's stated intent), or add a clear "see also" header to each pointing at the other. Stop the silent two-artifacts-same-name situation.
2. **Promote the dual-queue + enqueuer-not-submitter + post-renderLists-hook trio from MEMORY.md into the consolidated contract.** These are the load-bearing renderer-architectural facts that everyone needs and nothing canonical documents. Treat the existing memory files as drafts.
3. **Resolve the Bucket A/B/C/D vs Track A/B/C terminology collision** before promoting Track terminology into the contract. Pick one vocabulary; cross-reference the other.
4. **Update Priority 1 / D1 framing in the high-level doc** to reflect that `terrain.cpp` no longer drives `projectZ`. Re-scope the remaining concern to whatever the actual residual is (probably "decide whether `quad.cpp` projectZ containment is the end state").
5. **Resolve D3** (post-process shadow as bridge vs as chosen path for non-terrain geometry) — the registry implementation and the high-level doc give different answers, and any future shadow work will land on whichever answer is current.
6. **Add a one-paragraph section in the consolidated contract for each of: compute cull, substrate coalesce, indirect terrain draw, water SSBO fast path.** They are the active modernization slices and they all interact with submission/visibility ownership. Without them in the contract, every new slice has to re-derive the relationship.
7. **Add the stock-install playability invariant as an explicit Non-Goal-style line.** One sentence, low effort, prevents future "modern sidecar required" regressions from being argued as in-bounds.
